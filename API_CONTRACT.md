# Zero-Touch App Understanding
## Official System API Contract

Version: 1.0 (Phase 1 → Phase 2)  
Status: Approved  

---

# 1. Overview & Purpose

This document defines the official, shared communication contracts between the core modules of the **Zero-Touch App Understanding** system:

1. **Android Controller** (`android-controller/`) — The "eyes and hands" (device automation, screen capture, hierarchy extraction).
2. **Exploration Agent** (`agent/`) — The "brain" (screen understanding, exploration memory, action selection).
3. **Knowledge Pack & Dashboard** (`knowledge/`, `dashboard/`) — The "memory and showcase" (topology graph, knowledge blueprint, visualization, UI reconstruction).

All cross-module interfaces must strictly conform to the schemas, validation rules, and data mappings specified herein.

---

# 2. Controller → Agent: Screen State

Whenever the Android Controller captures device state (upon initial app launch or following action execution), it produces a standardized `ScreenState` payload.

### JSON Schema

```json
{
  "screenshot_path": "screenshots/screen_001.png",
  "current_activity": "com.example.app/.MainActivity",
  "elements": [
    {
      "element_id": "com.example.app:id/search_button",
      "type": "android.widget.Button",
      "text": "Search",
      "content_description": "Search products",
      "bounds": [100, 200, 900, 300],
      "center": [500, 250],
      "clickable": true,
      "scrollable": false,
      "focusable": false,
      "enabled": true
    }
  ]
}
```

### Field Definitions & Requirements

#### Top-Level `ScreenState`
| Field | Type | Requirement | Description |
| :--- | :--- | :--- | :--- |
| `screenshot_path` | `string` | **Required** | Relative or absolute path to the captured PNG screenshot. Empty string if screenshot capture was explicitly bypassed. |
| `current_activity`| `string` | **Required** | Foreground Android package and activity component (e.g. `com.example.app/.MainActivity` or `com.example.app/com.example.app.SearchActivity`). |
| `elements` | `array[UIElement]` | **Required** | List of parsed and filtered UI elements discovered on the screen. |

#### Nested `UIElement`
| Field | Type | Requirement | Description |
| :--- | :--- | :--- | :--- |
| `element_id` | `string` | **Required** | Android `resource-id` (e.g. `com.example.app:id/btn_login`) or a deterministic fallback ID (e.g. `elem_002_Button_100_200`) generated by `UIParser`. Must be unique within the screen. |
| `type` | `string` | **Required** | Android widget class name (e.g. `android.widget.Button`, `android.widget.EditText`, `android.widget.TextView`, `androidx.recyclerview.widget.RecyclerView`). |
| `text` | `string` | Optional | Visible text displayed inside or on the widget. Defaults to `""`. |
| `content_description` | `string` | Optional | Accessibility content description (`android:contentDescription`). Defaults to `""`. |
| `bounds` | `array[int]` | **Required** | Exact screen coordinates `[x1, y1, x2, y2]` where `(x1, y1)` is top-left and `(x2, y2)` is bottom-right. |
| `center` | `array[int]` | **Required** | Clickable center coordinates `[x, y]` computed as `[(x1 + x2) // 2, (y1 + y2) // 2]`. |
| `clickable` | `boolean` | **Required** | Whether the element responds to click/touch events. |
| `scrollable` | `boolean` | **Required** | Whether the element can be scrolled. |
| `focusable` | `boolean` | **Required** | Whether the element can receive input focus. |
| `enabled` | `boolean` | **Required** | Whether the element is enabled for interaction. |

# 3. Agent → Controller: Action

After evaluating the current `ScreenState` and exploration memory, the Agent returns an `AgentAction` instruction dictating the next physical interaction.

### General Structure

```json
{
  "action": "<action_type>",
  "target": {
    "element_id": "<target_element_id>"
  },
  "parameters": {}
}
```

### Supported Actions & Schemas

#### 3.1 `tap`
Simulates a single touch tap at the resolved coordinates of `element_id` or explicit coordinates.

* **Required Fields**:
  - `action`: `"tap"`
  - `target.element_id` **or** `target.coordinates`: Target element identifier or `[x, y]` integer pair.
* **Example**:
```json
{
  "action": "tap",
  "target": {
    "element_id": "com.example.app:id/search_button"
  }
}
```

#### 3.2 `type`
Enters text into an editable input field. If `target.element_id` is provided, the controller taps the field first to request focus before typing.

* **Required Fields**:
  - `action`: `"type"`
  - `parameters.text`: Text string to enter.
* **Optional Fields**:
  - `target.element_id`: Target `EditText` element to focus.
* **Example**:
```json
{
  "action": "type",
  "target": {
    "element_id": "com.example.app:id/search_input"
  },
  "parameters": {
    "text": "tiger"
  }
}
```

#### 3.3 `scroll`
Performs a swipe gesture to scroll content.

* **Required Fields**:
  - `action`: `"scroll"`
  - `parameters.direction`: One of `"down"`, `"up"`, `"left"`, `"right"`.
* **Optional Fields**:
  - `target.element_id`: Scroll inside a specific scrollable container (e.g. `RecyclerView`). If omitted, scrolls center viewport.
  - `parameters.duration_ms`: Duration of swipe gesture in milliseconds (default: `300`).
* **Example**:
```json
{
  "action": "scroll",
  "parameters": {
    "direction": "down",
    "duration_ms": 400
  }
}
```

#### 3.4 `back`
Presses the physical/system Android Back button (`KEYCODE_BACK = 4`).

* **Required Fields**:
  - `action`: `"back"`
* **Example**:
```json
{
  "action": "back"
}
```

#### 3.5 `wait`
Pauses execution to allow animations, network requests, or UI transitions to settle.

* **Required Fields**:
  - `action`: `"wait"`
* **Optional Fields**:
  - `parameters.duration_ms`: Wait duration in milliseconds (default: `1000`).
* **Example**:
```json
{
  "action": "wait",
  "parameters": {
    "duration_ms": 1000
  }
}
```

#### 3.6 `stop`
Instructs the controller that exploration has completed or reached terminal conditions.

* **Required Fields**:
  - `action`: `"stop"`
* **Example**:
```json
{
  "action": "stop"
}
```

# 4. Controller → Agent: Action Result

After executing the requested action, the Android Controller waits for UI stabilization and returns an `ActionResult` payload containing execution status and the resulting screen state.

### JSON Schema

```json
{
  "success": true,
  "action_executed": {
    "action": "tap",
    "element_id": "com.example.app:id/search_button"
  },
  "state": {
    "screenshot_path": "screenshots/screen_002.png",
    "current_activity": "com.example.app/.SearchActivity",
    "elements": []
  },
  "error": null
}
```

### Field Definitions

| Field | Type | Requirement | Description |
| :--- | :--- | :--- | :--- |
| `success` | `boolean` | **Required** | `true` if action executed without ADB/subprocess failure; `false` if an error occurred. |
| `action_executed` | `object` | **Required** | Summary of the action that was actually run. |
| `state` | `object (ScreenState)` | **Required on success** | Resulting screen state after action execution and stabilization. Contains updated screenshot, activity, and elements. |
| `error` | `string` or `null` | **Required on failure** | Error description if `success` is `false` (e.g. element not found, ADB timeout); `null` otherwise. |

### Failure Behavior
- If `target.element_id` does not exist on the current screen, `success` is `false`, `error` contains `Target element '<id>' not found`, and `state` reflects the unchanged screen.
- The Agent catches the failure, marks that action as failed in `ExplorationMemory`, and selects an alternative action without crashing the loop.

# 5. Observation → Knowledge Pack Mapping

The Knowledge Pack stores permanent, reusable application representations. When a `ScreenState` is observed and understood by the Agent, it is mapped into `ScreenData` within the `KnowledgeBuilder`.

### Direct Field Mapping

```
Controller ScreenState                         Knowledge Pack ScreenData
──────────────────────                         ─────────────────────────
screenshot_path          ───────────────►      screenshot_path
current_activity         ───────────────►      activity_name
elements                 ───────────────►      elements (UIElementData list)
  ├── element_id         ───────────────►        ├── element_id
  ├── type               ───────────────►        ├── type
  ├── text               ───────────────►        ├── text
  ├── content_description───────────────►        ├── content_description
  ├── bounds             ───────────────►        ├── bounds
  ├── center             ───────────────►        ├── center
  ├── clickable          ───────────────►        ├── clickable
  ├── scrollable         ───────────────►        ├── scrollable
  ├── focusable          ───────────────►        ├── focusable
  └── enabled            ───────────────►        └── enabled
```

### Semantic Enrichment by Agent
The Agent synthesizes high-level understanding that the Controller cannot extract directly from ADB/UIAutomator:

| Knowledge Pack Field | Source | Description / Example |
| :--- | :--- | :--- |
| `screen_id` | Agent / System | Canonical ID (e.g. `"screen_001"`). |
| `name` | Agent Understanding | Human-readable screen title (e.g. `"Login"`, `"Home Feed"`, `"Search"`). |
| `purpose` | Agent Understanding | Concise explanation of screen role (e.g. `"Allows users to enter credentials"`). |
| `elements[i].purpose`| Agent Understanding | Semantic purpose of individual widgets (e.g. `"Submits login form"`). |
| `actions[i]` | Agent Understanding | List of mapped actionable triggers with human-readable descriptions. |
| `design` | Agent / Perception | Extracted design tokens (e.g. `{"theme": "dark", "layout_type": "feed"}`). |

# 6. Navigation Transitions

A `TransitionData` record captures a directed edge in the application graph when an action on a source screen leads to a destination screen.

### JSON Schema

```json
{
  "transition_id": "trans_001",
  "source_screen_id": "screen_001",
  "action": {
    "action_type": "tap",
    "target_element_id": "com.example.app:id/search_button",
    "parameters": {},
    "description": "Tap on Search icon"
  },
  "destination_screen_id": "screen_002",
  "status": "success",
  "timestamp": 1773792040.0
}
```

### Field Definitions

| Field | Type | Requirement | Description |
| :--- | :--- | :--- | :--- |
| `transition_id` | `string` | **Required** | Unique transition ID (e.g. `"trans_001"`). |
| `source_screen_id` | `string` | **Required** | Canonical ID of the screen where the action was initiated. |
| `action` | `object` | **Required** | The action executed (`action_type`, `target_element_id`, `description`). |
| `destination_screen_id`| `string` | **Required** | Canonical ID of the screen observed after action completion. |
| `status` | `string` | **Required** | `"success"` (screen changed or confirmed state), `"no_change"`, or `"failed"`. |
| `timestamp` | `float` | Optional | Unix epoch seconds when the transition occurred. |

# 7. Screen Identity & Deduplication (Phase 2)

To decide whether an observed `ScreenState` is a **NEW screen** or an **ALREADY-KNOWN screen**, Phase 2 uses a deterministic, rule-based signature. No heavy computer vision or external models are required.

### Deterministic Fingerprint Algorithm

For any observed screen $S$, compute its fingerprint tuple:

$$\text{Fingerprint}(S) = (\text{Activity}, \text{ElementSetHash}, \text{InteractiveTextSet})$$

1. **Activity Match**:
   Compare `current_activity` (e.g. `com.example.shop/.MainActivity`). If activities differ, screens are considered distinct (unless explicitly aliased).
2. **Structural Element Signature**:
   Collect all non-empty `resource_id`s or fallback IDs sorted alphabetically. Compute SHA-256 hash or set equivalence:
   ```python
   element_ids = sorted([e["element_id"] for e in elements if e.get("element_id")])
   ```
3. **Interactive Text & Title Match**:
   Collect text from prominent headers and clickable elements:
   ```python
   titles = {e["text"].strip().lower() for e in elements if e.get("clickable") and e.get("text")}
   ```

### Classification Rules

- **Existing Screen Match**:
  If `current_activity` matches an existing screen AND the Jaccard similarity of interactive element IDs $\ge 0.85$, the screen is classified as an **already-known screen**. The system re-uses the existing `screen_id`.
- **New Screen**:
  If `current_activity` is novel OR element ID overlap $< 0.85$, generate a new `screen_id` (e.g. `screen_003`), register it in `ExplorationMemory` and `KnowledgeBuilder`.

# 8. Module Responsibilities

The system maintains strict separation of concerns across the three modules:

```
┌────────────────────────────────────────────────────────┐
│                   ANDROID CONTROLLER                   │
│  - Physical ADB subprocess execution                   │
│  - Device discovery & connection                       │
│  - Screenshot capture (screencap)                      │
│  - UIAutomator XML hierarchy extraction                │
│  - Low-level touch/key gestures (tap, swipe, keyevent) │
└──────────────────────────┬─────────────────────────────┘
                           │ ScreenState / ActionResult
                           ▼
┌────────────────────────────────────────────────────────┐
│                   EXPLORATION AGENT                    │
│  - Screen classification & deduplication               │
│  - Semantic interpretation of purpose & elements       │
│  - Exploration memory (visited screens, attempted acts)│
│  - Action selection algorithm (unexplored priority)    │
│  - Action validation & safety boundaries               │
└──────────────────────────┬─────────────────────────────┘
                           │ ScreenData / TransitionData
                           ▼
┌────────────────────────────────────────────────────────┐
│              KNOWLEDGE PACK & DASHBOARD                │
│  - Persistent Knowledge Pack assembly (JSON schema)    │
│  - Navigation graph topology construction              │
│  - Web-based 3-column interactive visual dashboard     │
│  - Screenshot bounding-box inspector                   │
│  - Autonomous HTML/CSS UI reconstruction engine        │
└────────────────────────────────────────────────────────┘
```

# 9. Phase 2 Autonomous Exploration Loop

The end-to-end autonomous integration loop operates as follows:

```
                      ┌──────────────────────┐
                      │    START / RESUME    │
                      └──────────┬───────────┘
                                 │
                                 ▼
                     [ 1. OBSERVE APP STATE ]
                                 │
     CONTROLLER executes screenshot() + dump_ui_hierarchy()
                                 │
                                 ▼
                     [ 2. EMIT SCREEN STATE ]
                   Controller produces ScreenState
                                 │
                                 ▼
                     [ 3. INGEST & DEDUPLICATE ]
                     Agent receives ScreenState
              Checks fingerprint against ExplorationMemory
                    Identifies screen_id (new vs known)
                                 │
                                 ▼
                     [ 4. DECIDE NEXT ACTION ]
             Agent prioritizes unvisited interactive elements
                 Generates Action (tap, type, scroll, back)
                   Or emits 'stop' if goal reached
                                 │
                                 ▼
                     [ 5. EXECUTE ACTION ]
                    Controller executes input
                    Waits stabilization_time
                   Returns ActionResult + new State
                                 │
                                 ▼
                     [ 6. RECORD KNOWLEDGE ]
             Knowledge Builder registers new ScreenData
                 Records TransitionData (src -> dst)
                 Updates Navigation Graph in real-time
                                 │
                                 ▼
                     [ 7. UPDATE MEMORY ]
             Agent records attempted action & destination
                                 │
                                 ▼
                     [ 8. REPEAT OR TERMINATE ]
              If action == 'stop' -> Finalize Knowledge Pack
              Else -> Loop back to Step 1
```
